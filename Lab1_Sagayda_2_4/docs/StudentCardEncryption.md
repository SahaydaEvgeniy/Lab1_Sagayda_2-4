# Шифрування номера студентського квитка

## Перевірка в застосунку

1. Зупиніть локальний API через Ctrl+C та запустіть його знову, щоб він зібрав
   оновлений код:

   ```powershell
   dotnet run --project tools/StudentSyncApi/StudentSyncApi.csproj
   ```

2. Повністю перезапустіть MAUI-застосунок через Shift+F5 і F5.
3. Додайте студента з номером квитка, наприклад `TEST-CARD-2026-123`.
4. Відкрийте деталі та перевірте номер. Змініть його й збережіть.
5. Закрийте й відкрийте застосунок: номер має залишитися доступним.
6. Змініть номер і поверніться кнопкою «Назад» без збереження: має залишитися
   попередній номер. Чернетка при згортанні зберігає і номер, і бал.
7. Синхронізуйте. На http://127.0.0.1:5080/students має бути поле
   `studentCardNumberEncrypted` зі значенням `v1:...`, а відкритого номера бути не повинно.
   Дані операцій можна переглянути на http://127.0.0.1:5080/sync/operations.

Номер необов'язковий, до 64 символів. Для старих студентів він початково порожній.
Введення номера не змінює Id студента та не порушує deep link.

## Реалізація

`Student.StudentCardNumber` використовується лише в пам'яті й інтерфейсі.
Атрибути `SQLite.Ignore` та `JsonIgnore` виключають його зі схеми SQLite та
JSON-серіалізації. `StudentCardNumberEncrypted` є окремим збереженим полем.

`StudentCardProtection` реалізує `IStudentCardProtection`. Перед записом
репозиторій створює окрему копію студента із зашифрованим полем. Зміна студента
та знімок у SyncQueue записуються однією транзакцією. Після читання з SQLite
номер розшифровується для інтерфейсу. Delete бере вже зашифрований запис із БД.

Використано AES-256-GCM, випадковий nonce на 12 байтів і тег автентичності
на 16 байтів. Формат: `v1:` та Base64 від `nonce | tag | ciphertext`.
AAD містить Id студента, назву поля й версію формату, щоб підміна номера
між різними записами не проходила перевірку автентичності.

Ключ на 32 випадкові байти зберігається через `SecureStorage` за ключем
`student_card_aes256_v1`, окремо від SQLite й репозиторію Git. Він не надсилається
на сервер. Кожне шифрування використовує новий nonce. Порожній номер зберігається
як порожнє значення без створення ключа.

При пошкодженому шифротексті або відсутньому ключі читання завершується помилкою;
номер не підміняється порожнім значенням. Якщо SecureStorage не зміг зберегти ключ,
запис студента та операція черги не створюються. У тестах криптографії інтерфейс
SecureStorage підміняється тестовим сховищем; реальне платформне сховище
перевіряється запуском застосунку й повторним відкриттям номера після перезапуску.

## Міграція і синхронізація

Версія SQLite підвищується до 4; додається лише зашифрована колонка.
Старі студенти та операції черги залишаються на місці. Дані попередніх операцій
не змінюються, щоб збереглася ідемпотентність за OperationId.

API приймає й зберігає шифротекст як непрозоре значення та не має ключа для
його розшифрування. Сервер із кроку 6 оголошує
`supportsEncryptedStudentCards: true` у `/health`. Перед першим надсиланням
непорожнього зашифрованого поля за один сеанс синхронізації клієнт перевіряє цю
ознаку. Старий запущений API не зможе непомітно підтвердити й відкинути це поле:
операція залишиться в черзі, а інтерфейс запропонує перезапустити сервер.

Сумісність повторних операцій, прийнятих попереднім API без нового поля,
зберігається: відсутнє необов'язкове поле не додається до канонічного JSON.
Шифрується саме номер квитка, не вся база даних і не інші поля студента.
