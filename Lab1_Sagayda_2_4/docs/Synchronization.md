# Синхронізація з локальним API

## Запуск

У PowerShell із папки MAUI-проєкту виконайте та залиште термінал відкритим:

```powershell
dotnet run --project tools/StudentSyncApi/StudentSyncApi.csproj
```

Потім запустіть застосунок через Visual Studio. На головній сторінці є кнопка
«Синхронізувати», кількість операцій, індикатор виконання та текстовий результат.
Спроба також запускається автоматично після запуску застосунку та при появі
локальної мережі або інтернет-з'єднання, а також після повернення застосунку з фону.

Адреси API:
- Windows: `http://127.0.0.1:5080/`.
- Android-емулятор: `http://10.0.2.2:5080/`.

На Android HTTP дозволений лише для адрес локального сервера через
`network_security_config.xml`. Фізичний телефон потребує окремого налаштування адреси;
`10.0.2.2` призначено для стандартного Android-емулятора.

## Перевірка

1. Із запущеним сервером додайте студента й натисніть «Синхронізувати».
2. Лічильник має стати нульовим, а http://127.0.0.1:5080/students у браузері
   комп'ютера має містити цього студента. Оновіть сторінку браузера вручну.
3. Змініть бал зі збереженням, синхронізуйте й перевірте новий бал на сервері.
4. Видаліть студента, синхронізуйте й перевірте його відсутність на сервері.
5. Зупиніть сервер через Ctrl+C. Додайте студента в застосунку та синхронізуйте.
   Має бути повідомлення про недоступність сервера, а операція має залишитися в черзі.
6. Запустіть сервер знову та натисніть «Синхронізувати». Черга має зменшитися до нуля.
   Сам перезапуск сервера не є подією зміни мережі, тому в цьому сценарії потрібна кнопка.
7. Для перевірки автоматичної спроби на Android вимкніть мережу, створіть зміни,
   потім відновіть мережу із запущеним сервером. Увімкнення режиму польоту має
   супроводжуватися вимкненням Wi-Fi. Працюйте з відкритим застосунком.

Якщо сервер був доступний під час запуску застосунку, черга могла надіслатися
автоматично ще до натискання кнопки. Відсутність інтернету в Windows не заважає
доступу до сервера на тому самому комп'ютері; зупинка сервера є надійним тестом помилки.

## Гарантії та межі

Операції надсилаються послідовно за Sequence. Кожна містить початкові OperationId,
StudentId, тип операції, знімок даних і час створення UTC. Після читання SQLite
ознака UTC відновлюється без зміщення збережених ticks.

Запис видаляється з SyncQueue лише після успішної HTTP-відповіді з відповідними
OperationId та StudentId і допустимим підтвердженням Applied, Duplicate або IgnoredOlder.
Помилка мережі, таймаут, відмова сервера або некоректне підтвердження зупиняють
обробку; поточна та наступні операції залишаються в черзі. Уже підтверджені операції
не повертаються в чергу. Якщо сервер прийняв зміну, але видалення її з локальної
черги не вдалося, повтор із тим самим OperationId отримає Duplicate.

Паралельні запуски сервісу серіалізовані. Зміни, додані під час синхронізації,
обробляються наступним проходом. Застосунок залишається придатним до локальних
CRUD-операцій. Після зміни мережі виконується нова спроба; постійного фонового
таймера або WorkManager немає, виконання після завершення процесу не гарантується.

Це надсилання локальних змін на сервер. Зворотне завантаження записів із сервера
не реалізоване. Сервер застосовує «останнє оновлення перемагає»; IgnoredOlder
підтверджує обробку старішої операції, але не перезаписує локального студента
серверною версією. Про такі результати повідомляється в статусі синхронізації.
